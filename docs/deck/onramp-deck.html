Team and project introductionOnRamp · 1
The developer problem

The suite is red. Did you break it, or was it already broken?

29 / 1,761

Healthchecks tests fail on Windows before anyone changes a line.

Healthchecks is an open-source Django app. 26 tests need socket.AF_UNIX, 2 use a Linux-only date format and 1 needs time-zone switching. The team's Linux run passes all of them.

  • Newcomers inherit large repositories, local quirks and test suites that already fail on their machine.
  • AI agents make plausible changes fast. "It passes" is not evidence when the baseline is already red.
  • Without a baseline, a reviewer must trust the agent or redo the work.
Our question: can IBM Bob onboard onto unfamiliar code, fix a real bug and add a real feature, so that every claim can be checked?

What we built

OnRamp: one folder you drop into a repository

Step 1
/onrampValidates the install, writes a repo profile, captures the baseline and maps the codebase.
Step 2
Explorer modeRead-only guide with file references. It answers "where does X live?" before any change.
Step 3
Reproducer modeFailing test first. The fix comes only after the pre-fix artefact shows FAIL.
Step 4
Verifier modeRe-runs the tests and classifies each failure against the baseline: inherited, regression or fixed.
Step 5
Evidence reportPre-fix failure, post-fix pass, diff and REPORT_<slug>.md for the reviewer.

Regression found in step 4 → back to the fix. No new failures → evidence report.

Impact for teams and enterprises

Reviewers check evidence instead of trusting the agent

Faster onboarding

A newcomer runs /onramp. Explorer mode and the map-codebase skill map the repository read-only before anyone changes it.

Reviewable AI changes

Every change ships with a pre-fix failure, a post-fix pass, a diff and a report. A reviewer can re-run each claim.

Less test noise

The baseline separates failures that were already there from regressions the change introduced. 29 inherited failures stop blocking work.

Drop-in adoption

One .bob/ folder and a per-repository profile. No new service to run.

Agent benchmarking

Sealed blind briefs compare an AI fix with the maintainer's real fix, on the same bug.

Audit trail

Every Bob commit carries Generated-by: IBM Bob. Bob's task log is exported as evidence.

Roadmap and learnings

Next: turn the rules into gates

1

PreToolUse gate: block production edits until a failing-test artefact exists.
Today the mode rules are instructions. When Verifier refused a production edit, Bob switched itself to Agent mode.

2

Fail-closed verifier: a crashed or partial run must fail, not pass silently.
The team-written onramp_normalize.py classify already fails closed.

3

pytest support: profiles for pytest projects, then Node and Java.

4

CI and benchmarks: classify every pull request; add blind benchmarks from real upstream fixes.

Learnings

  • A baseline is the difference between "tests are red" and "I broke something".
  • A narrow check misses regressions. Bob's first check ran one app; Verifier's wider run found the 22 errors.
  • Sealing the brief makes an AI fix comparable with a human one.
  • A second repository exposes what a single repository hides.

Known limitations: see README.
