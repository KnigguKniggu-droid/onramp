Team and project introduction1
The developer problem

In a real codebase, red tests don't tell you whether you broke something.

  • Newcomers inherit large repositories, local quirks and test suites that already fail on their machine.
  • Healthchecks (10k-star Django app): 29 of 1,761 tests fail on Windows before anyone changes a line.
  • AI assistants make plausible changes fast, but "it passes" is not evidence when the baseline is red.

Question: can IBM Bob onboard onto unfamiliar code, fix a real bug and add a real feature, so that every claim can be checked?

Why it matters

Brownfield onboarding is where developers lose the most time, and where trust in an AI partner is earned or lost. OnRamp makes Bob's work reproducible: baseline first, failing test before fix, and a report a reviewer can verify.

What we built

OnRamp: one folder you drop into a repository

/onrampValidates the install, writes a repo profile, captures a baseline, maps the codebase.
Explorer modeRead-only guide with file references; cannot edit or run anything.
Reproducer modeFailing test first; the fix comes only after the pre-fix artifact exists.
Verifier modeRe-runs tests and classifies every failure: inherited, regression, fixed, unchanged.
EvidenceStdlib generator: sealed blind benchmarks, attached reference patches, REPORT_<slug>.md.
Built entirely from Bob extension points: .bob/custom_modes.yaml, 4 skills, 2 commands, a PostToolUse hook in .bob/settings.json and .bob/gen_report.py (49 tests).

How Bob was used

IBM Bob as the engineering partner, end to end

  • Plan mode designed the kit and asked 4 design questions before building.
  • Agent mode built the modes, skills, commands, hook and generator, each in its own commit.
  • Custom modes (Reproducer, Verifier) drove the blind fix.
  • Bob Shell (ACP) ran the portability tests in other repositories.

Process, honestly

Claude Code operated Bob at the participant's direction, verified each result independently (full suites, revert checks, baseline diffs) and reported only observed failures back. Every one of Bob's commits ends with Generated-by: IBM Bob.

Roadmap and learnings

What we learned, and what comes next

Learnings

  • A baseline is the difference between "tests are red" and "I broke something".
  • Sealing the brief makes an AI fix comparable with a human one.
  • Bob's first plan guessed config locations; testing the kit on a second repository exposed what a single repo hides.
  • Budget discipline: small, fresh Bob tasks cost a fraction of long ones.

Roadmap

  • Profiles for pytest, Node and Java projects.
  • Record allowed and withheld information in every sealed benchmark.
  • A CI job that runs gen_report.py classify on every pull request.
  • More blind benchmarks from real upstream fixes, to score agents over time.
